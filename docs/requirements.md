# 콘서트 예약 서비스 요구사항

## 1. 문서 목적

이 문서는 JPA 기반 콘서트 예약 서비스의 기능 요구사항, 비기능 요구사항, 정책 결정 사항, 상태 흐름, 만료 처리 전략, 구현 우선순위를 정리한 최종 설계 문서다.

본 설계는 아래 전제를 기준으로 한다.

- 유저는 사전에 존재한다.
- 날짜는 회차와 동일한 의미로 사용한다.
- 한 공연장에서는 하루 하나의 콘서트만 열린다고 가정한다.
- 좌석 번호는 회차별 1번부터 50번까지 고정이다.
- 좌석 가격은 고정이다.
- 한 사용자는 동시에 하나의 임시 배정만 가질 수 있다.

## 2. 기능 요구사항

### 2.1 유저 대기열 토큰 기능

- 사용자는 콘서트별 대기열 토큰을 발급받을 수 있어야 한다.
- 사용자는 자신의 콘서트별 대기번호를 조회할 수 있어야 한다.
- 토큰은 유저와 콘서트 기준으로 발급된다.
- 토큰 검증은 모든 API가 아니라 좌석 예약과 결제 API에서만 수행한다.
- 대기열은 글로벌이 아니라 콘서트별로 독립적으로 관리한다.

### 2.2 예약 가능 날짜 및 좌석 조회 기능

- 사용자는 특정 콘서트의 예약 가능한 날짜 목록을 조회할 수 있어야 한다.
- 사용자는 특정 날짜의 예약 가능한 좌석 목록을 조회할 수 있어야 한다.
- 조회 결과에서 이미 확정된 좌석은 제외되어야 한다.
- 조회 결과에서 임시 배정 중이며 아직 만료되지 않은 좌석은 제외되어야 한다.

### 2.3 좌석 예약 요청 기능

- 사용자는 날짜와 좌석 번호를 입력해 좌석 예약을 요청할 수 있어야 한다.
- 예약 요청 성공 시 좌석은 즉시 확정되지 않고 약 5분 동안 임시 배정 상태가 되어야 한다.
- 임시 배정 상태의 좌석은 다른 사용자가 선점할 수 없어야 한다.
- 임시 배정 시간이 지나도록 결제가 완료되지 않으면 좌석은 다시 예약 가능 상태로 돌아가야 한다.
- 같은 사용자는 동시에 둘 이상의 임시 배정을 보유할 수 없어야 한다.

### 2.4 잔액 충전 및 조회 기능

- 사용자는 자신의 잔액을 충전할 수 있어야 한다.
- 사용자는 자신의 현재 잔액을 조회할 수 있어야 한다.

### 2.5 결제 기능

- 사용자는 자신이 임시 배정한 좌석에 대해 결제를 요청할 수 있어야 한다.
- 결제 시 고정 좌석 가격만큼 잔액이 차감되어야 한다.
- 결제 성공 시 결제 내역이 생성되어야 한다.
- 결제 성공 시 좌석은 최종 확정 상태가 되어야 한다.
- 결제 성공 시 해당 대기열 토큰은 만료 또는 사용 완료 처리되어야 한다.

## 3. 비기능 요구사항

### 3.1 정합성

- 다수 인스턴스 환경에서도 같은 좌석이 중복 배정되지 않아야 한다.
- 결제 중 잔액이 중복 차감되지 않아야 한다.
- 만료 시점과 사용자 요청이 충돌하더라도 최종 상태가 일관되어야 한다.

### 3.2 동시성

- 좌석 선점, 결제, 잔액 차감은 동시 요청을 고려해 설계해야 한다.
- 애플리케이션 인메모리 락에 의존하지 않고 DB 정합성으로 제어해야 한다.

### 3.3 확장성

- 대기열, 좌석, 결제 처리는 여러 인스턴스에서 동작해도 동일한 결과를 보장해야 한다.
- 스케줄러는 정리 용도로만 사용하고 실제 판정은 요청 처리 트랜잭션 안에서 수행해야 한다.

### 3.4 테스트

- 아래 기능 각각에 대해 최소 1개 이상의 단위 테스트가 필요하다.
- 대기열 토큰 발급 및 조회
- 예약 가능 날짜 조회
- 예약 가능 좌석 조회
- 좌석 임시 배정
- 잔액 충전
- 잔액 조회
- 결제 성공
- 결제 실패 또는 제약 조건 검증

## 4. 정책 결정 사항

### 4.1 토큰 정책

- 토큰은 좌석 예약 API와 결제 API에서만 필수다.
- 토큰은 콘서트별로 발급된다.
- 대기열은 콘서트별로 독립 운영된다.
- 콘서트별 `ACTIVE` 토큰 수는 설정값으로 제한한다.
- `ACTIVE` 슬롯이 비는 조건은 결제 성공에 따른 `USED`, 유효시간 경과에 따른 `EXPIRED`, 운영 정책에 따른 강제 종료다.
- `WAITING` 토큰은 현재 `ACTIVE` 수가 최대 슬롯 수보다 작을 때만 승격 대상이 된다.
- 승격 대상은 가장 작은 `queuePosition`을 가진 `WAITING` 토큰부터 선택한다.
- 승격은 대기번호 조회, 예약 또는 결제 직전 토큰 검증 보정 로직, 스케줄러에서 시도할 수 있다.
- 어떤 경로에서 승격을 시도하더라도 최종 승격 여부는 같은 트랜잭션 안에서 활성 슬롯 수를 재검증해 결정한다.
- 결제 완료 시 해당 토큰은 더 이상 사용할 수 없도록 만료 또는 사용 완료 처리한다.

### 4.2 공연 및 좌석 정책

- 날짜는 회차와 동일하다.
- 한 공연장에서는 하루 하나의 콘서트만 존재한다고 가정한다.
- 좌석은 회차별 1번부터 50번까지 존재한다.
- 좌석 가격은 고정값으로 관리한다.
- 한 사용자는 동시에 하나의 임시 배정만 허용한다.

### 4.3 만료 정책

- 임시 배정 만료는 스케줄러와 요청 시점 재검증을 병행한다.
- 스케줄러는 만료 상태를 정리하는 보조 수단이다.
- 실제 정합성 판정은 예약과 결제 트랜잭션 내부에서 수행한다.

## 5. 상태 흐름

### 5.1 대기열 토큰 상태 흐름

`WAITING -> ACTIVE -> USED`

또는

`WAITING -> ACTIVE -> EXPIRED`

설명:

- `WAITING`: 대기열에 들어간 상태
- `ACTIVE`: 예약 또는 결제가 가능한 상태
- `USED`: 결제 성공으로 사용 완료된 상태
- `EXPIRED`: 유효시간 경과 등으로 사용할 수 없는 상태
- `ACTIVE` 승격은 콘서트별 활성 슬롯이 남아 있을 때만 가능하다

### 5.1.1 대기열 승격 정책

- 콘서트별로 동시에 예약 또는 결제가 가능한 `ACTIVE` 슬롯 최대 수를 둔다.
- 현재 `ACTIVE` 상태 토큰 수가 최대 수 미만이면 `WAITING` 토큰을 승격할 수 있다.
- 슬롯이 비는 시점은 `USED`, `EXPIRED`, 강제 종료 상태 반영 시점이다.
- 승격 대상은 가장 앞선 대기순번의 `WAITING` 토큰이다.
- 승격 수행 시점은 아래 중 하나 또는 복합 방식으로 잡는다.
- 대기번호 조회 API 호출 시
- 예약 또는 결제 API에서 토큰 검증 직전 보정 로직 수행 시
- 별도 스케줄러 또는 배치 실행 시
- 승격 시도는 보정 성격이며, 최종 성공 여부는 트랜잭션 안에서 활성 슬롯 수 재검증으로 결정한다.

### 5.2 좌석 상태 흐름

`AVAILABLE -> HELD -> RESERVED`

또는

`AVAILABLE -> HELD -> AVAILABLE`

설명:

- `AVAILABLE`: 예약 가능한 상태
- `HELD`: 임시 배정 상태
- `RESERVED`: 결제 완료로 확정된 상태

### 5.3 예약 상태 흐름

`TEMPORARY -> CONFIRMED`

또는

`TEMPORARY -> EXPIRED`

설명:

- `TEMPORARY`: 임시 배정 생성 직후 상태
- `CONFIRMED`: 결제 완료로 확정된 상태
- `EXPIRED`: 결제 없이 만료된 상태

## 6. 만료 처리 전략

### 6.1 기본 원칙

- 스케줄러는 정리 용도다.
- 실제 만료 여부는 예약 요청과 결제 요청 트랜잭션 안에서 현재 시각 기준으로 재검증한다.

### 6.2 스케줄러 역할

- 만료된 임시 배정을 주기적으로 정리한다.
- 만료된 예약 상태를 `EXPIRED`로 반영한다.
- 만료된 좌석 상태를 `AVAILABLE`로 되돌린다.

### 6.3 요청 시점 재검증 역할

- 좌석 예약 시 기존 임시 배정이 이미 만료되었는지 확인한다.
- 결제 시 임시 배정이 아직 유효한지 확인한다.
- 스케줄러 실행 지연이 있어도 올바른 결과를 반환해야 한다.

## 7. 구현 우선순위

### 7.1 1단계

- 상태 enum과 핵심 테이블 구조를 확정한다.
- 유니크 제약, 인덱스, version 필드를 포함한 DB 스키마를 설계한다.

### 7.2 2단계

- 좌석 임시 배정 기능을 구현한다.
- 조건부 업데이트 기반의 선점 로직을 먼저 완성한다.
- 한 사용자의 단일 임시 배정 제약을 반영한다.

### 7.3 3단계

- 잔액 충전과 잔액 조회를 구현한다.
- 결제 트랜잭션의 기반이 되는 잔액 엔티티와 이력을 정리한다.

### 7.4 4단계

- 결제 기능을 구현한다.
- 잔액 차감, 결제 내역 생성, 좌석 확정, 예약 확정을 하나의 트랜잭션으로 묶는다.

### 7.5 5단계

- 콘서트별 대기열 토큰 발급 및 대기번호 조회를 구현한다.
- 좌석 예약과 결제 API에 토큰 검증을 연결한다.

### 7.6 6단계

- 예약 가능 날짜 조회와 좌석 조회 API를 구현한다.
- 임시 배정과 확정 좌석이 올바르게 제외되도록 한다.

### 7.7 7단계

- 만료 스케줄러를 구현한다.
- 동시성 및 제약 조건 중심의 단위 테스트를 보강한다.
