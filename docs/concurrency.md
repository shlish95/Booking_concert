# 콘서트 예약 서비스 동시성 설계

## 1. 문서 목적

이 문서는 콘서트 예약 서비스의 동시성 위험 구간, 락 전략, 만료 처리 전략을 정리한다.

핵심 목표는 아래와 같다.

- 다중 인스턴스 환경에서 좌석 중복 배정을 방지한다.
- 잔액 차감 정합성을 보장한다.
- 스케줄러와 사용자 요청이 충돌해도 올바른 상태를 유지한다.

## 2. 동시성 위험 구간

### 2.1 같은 좌석에 대한 동시 예약 요청

상황:

- 서로 다른 사용자가 같은 회차의 같은 좌석을 거의 동시에 예약 요청한다.

위험:

- 둘 다 임시 배정 성공 처리되면 중복 예약이 발생한다.

대응:

- 좌석 선점은 조건부 업데이트를 우선 사용한다.
- 갱신 조건에 현재 상태와 만료 여부를 함께 포함한다.
- 업데이트 성공 건수가 1건일 때만 선점 성공으로 간주한다.

### 2.2 한 사용자의 다중 임시 배정 시도

상황:

- 같은 사용자가 거의 동시에 서로 다른 좌석을 예약 요청한다.

위험:

- 동시에 두 개 이상의 임시 배정을 가질 수 있게 된다.

대응:

- 예약 요청 전에 사용자의 활성 임시 배정 존재 여부를 확인한다.
- 다만 서비스 조회만으로는 다중 인스턴스 환경에서 완전 보장되지 않는다.
- 동시에 두 요청이 모두 조회를 통과한 뒤 서로 다른 좌석을 선점할 수 있다.
- 최종 판단은 트랜잭션 안에서 다시 검증해야 한다.
- 확장안으로 사용자 기준 락, 사용자 활성 홀드 전용 보조 테이블, 사용자별 조건부 업데이트 전략을 검토할 수 있다.

### 2.3 잔액 동시 차감

상황:

- 같은 사용자가 여러 결제를 동시에 요청한다.

위험:

- 잔액이 중복 차감되거나 음수로 내려갈 수 있다.

대응:

- `UserBalance.version` 기반 낙관적 락을 기본안으로 사용한다.
- 충돌 발생 시 재시도 또는 실패 응답으로 처리한다.

### 2.4 만료 직전 결제 요청

상황:

- 임시 배정 만료 시점 직전 또는 직후에 결제 요청이 들어온다.

위험:

- 이미 만료된 예약이 결제 성공 처리될 수 있다.
- 반대로 아직 유효한 예약이 잘못 실패할 수 있다.

대응:

- 결제 트랜잭션 안에서 현재 시각 기준으로 `expiresAt`을 재검증한다.
- 좌석 상태와 예약 상태를 모두 본인 소유 기준으로 다시 확인한다.

### 2.5 스케줄러와 사용자 요청 충돌

상황:

- 스케줄러가 만료 좌석을 해제하는 순간 사용자가 결제하거나 재예약을 시도한다.

위험:

- 상태가 서로 엇갈려 좌석, 예약, 결제 정보가 불일치할 수 있다.

대응:

- 스케줄러는 정리 역할만 수행한다.
- 실제 성공 여부는 요청 처리 트랜잭션의 재검증 결과로 결정한다.

### 2.6 토큰 중복 사용

상황:

- 같은 `ACTIVE` 토큰으로 여러 예약 또는 결제를 동시에 시도한다.

위험:

- 의도하지 않은 중복 작업이 가능해진다.

대응:

- 좌석 예약과 결제 시 토큰 상태를 확인한다.
- 결제 성공 시 토큰을 즉시 `USED` 또는 `EXPIRED`로 전환한다.
- 상태 전이는 트랜잭션 안에서 수행한다.

## 3. 락 전략

### 3.1 좌석 선점 전략

기본안:

- 조건부 업데이트를 우선 사용한다.

예시 개념:

- 현재 상태가 `AVAILABLE`인 경우만 `HELD`로 변경
- 또는 현재 상태가 `HELD`이지만 `holdExpiresAt < now` 인 경우만 재선점 허용

장점:

- 다중 인스턴스 환경에서 인메모리 락 없이 동작한다.
- DB 한 번의 갱신 결과로 선점 성공 여부를 판정할 수 있다.
- 좌석 경쟁이 심한 구간에서 비교적 단순하고 효율적이다.

주의점:

- 만료 조건을 쿼리에 정확히 반영해야 한다.
- 예약 이력 생성과 좌석 상태 변경의 트랜잭션 경계를 일관되게 유지해야 한다.

### 3.1.1 사용자 단일 임시 배정 제약 확장안

기본 인식:

- `한 사용자는 동시에 하나의 임시 배정만 가능` 규칙은 단순 조회 조건이 아니라 동시성 제약이다.
- 좌석별 조건부 업데이트만으로는 사용자 단위 중복 홀드를 완전히 막지 못할 수 있다.

확장안:

- 사용자 기준 비관적 락 또는 논리 락 도입
- 사용자 활성 홀드 전용 보조 테이블 도입 후 `user_id` unique 제약 활용
- 사용자별 조건부 insert 또는 update 전략 도입

정리:

- 현재 기본안은 서비스 검증 + 트랜잭션 재검증이다.
- 부하 테스트에서 사용자 단위 경쟁이 의미 있게 발생하면 확장안을 우선 검토한다.

### 3.2 잔액 차감 전략

기본안:

- `UserBalance`에 낙관적 락을 적용한다.

이유:

- 잔액 충돌은 좌석 선점보다 상대적으로 경쟁 범위가 사용자 단위로 좁다.
- 일반적인 충전과 결제 흐름에서 낙관적 락이 구현 단순성과 성능 측면에서 유리하다.

처리 방식:

- 결제 시 잔액 엔티티를 읽는다.
- 잔액이 충분한지 검증한다.
- 차감 후 저장 시 `version` 충돌을 감지한다.
- 충돌 시 재시도 또는 실패 처리한다.

### 3.3 비관적 락 비교

비교 대상:

- `select for update` 기반 비관적 락

장점:

- 강한 직렬화 효과로 충돌 상황을 더 단순하게 다룰 수 있다.

단점:

- 대기 시간이 길어질 수 있다.
- 트래픽 증가 시 락 경합이 커질 수 있다.
- 장시간 트랜잭션에 취약하다.

정리:

- 현재 기본안은 잔액에 낙관적 락을 적용한다.
- 실제 부하 테스트 결과 충돌이 과도하면 비관적 락 전환을 비교 검토한다.

### 3.4 결제 확정 전략

기본안:

- 결제 확정은 트랜잭션 안에서 상태 검증으로 처리한다.

검증 대상:

- 토큰이 여전히 유효한지
- 예약이 본인 소유인지
- 예약이 만료되지 않았는지
- 좌석이 본인에게 임시 배정된 상태인지
- 잔액이 충분한지

원칙:

- 검증과 상태 변경은 반드시 같은 트랜잭션 안에서 수행한다.

## 4. 만료 처리 전략

### 4.1 기본 원칙

- 만료 처리는 스케줄러 + 요청 시점 재검증을 병행한다.
- 스케줄러는 정리 용도다.
- 실제 정합성 판정은 트랜잭션 내 재검증으로 처리한다.

### 4.2 스케줄러 처리 대상

- 만료된 `SeatInventory`의 `HELD` 상태 해제
- 만료된 `Reservation`의 `TEMPORARY` 상태를 `EXPIRED`로 변경
- 필요 시 만료된 토큰 정리

### 4.3 요청 시점 재검증 대상

- 좌석 예약 시 기존 홀드가 이미 만료되었는지
- 결제 시 예약과 좌석의 만료 시각이 아직 유효한지
- 토큰이 실제 사용 가능한 상태인지

### 4.4 설계 의도

- 스케줄러 지연이나 장애가 있어도 잘못된 결제 성공이 발생하지 않아야 한다.
- 만료 정리는 비동기일 수 있지만 정합성 판정은 동기적으로 보장해야 한다.

## 5. 구현 우선순위

### 5.1 1단계

- 좌석 선점용 조건부 업데이트 쿼리를 먼저 확정한다.
- 회차별 좌석 유니크 제약과 인덱스를 설계한다.

### 5.2 2단계

- 잔액 엔티티에 낙관적 락을 적용한다.
- 충돌 시 처리 정책을 정한다.

### 5.3 3단계

- 결제 트랜잭션의 상태 검증 순서를 구현한다.
- 좌석, 예약, 잔액, 토큰 변경을 하나의 흐름으로 묶는다.

### 5.4 4단계

- 만료 스케줄러를 구현한다.
- 스케줄러와 요청 충돌 시나리오 테스트를 추가한다.

### 5.5 5단계

- 좌석 중복 예약, 잔액 중복 차감, 만료 직전 결제 등의 동시성 테스트를 보강한다.
