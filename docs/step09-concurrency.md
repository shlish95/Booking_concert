# STEP09 - Concurrency
## 콘서트 예약 서비스의 동시성 문제 분석 및 DB 기반 해결 방안

---

## 1. 문서 목적

이 문서는 콘서트 예약 서비스에서 발생할 수 있는 동시성 문제를 식별하고,  
RDBMS 기반의 동시성 제어 방식(DB Lock, Optimistic Lock, Pessimistic Lock) 중  
비즈니스 로직에 적합한 방식을 선정하기 위해 작성하였다.

과제 요구사항에 따라 다음 내용을 다룬다.

- 서비스 내 동시성 문제 식별
- 문제 발생 원인 분석
- 해결 가능한 DB 메커니즘 비교
- 최종 해결 방식 선정
- 이후 구현 및 테스트 방향 정리

---

## 2. 서비스 배경

본 서비스는 콘서트 예약 서비스이며, 주요 흐름은 다음과 같다.

1. 유저는 대기열 토큰을 발급받는다.
2. 예약 가능한 공연 날짜/좌석을 조회한다.
3. 특정 좌석에 대해 예약 요청을 보낸다.
4. 좌석은 일정 시간 동안 임시 배정된다.
5. 유저는 자신의 잔액으로 결제를 진행한다.
6. 결제가 완료되면 좌석은 최종 확정된다.

이 구조에서는 동시에 같은 자원에 접근하는 요청이 발생할 수 있다.  
대표적으로 다음 두 영역에서 동시성 문제가 발생할 가능성이 높다.

- 좌석 선점(예약)
- 유저 잔액 차감

---

## 3. 동시성 문제 식별

### 3.1 좌석 선점(예약)

가장 대표적인 동시성 이슈는 **같은 좌석에 대한 중복 예약 시도**이다.

예시 상황:

- 사용자 A와 사용자 B가 동시에 같은 회차의 12번 좌석을 예약 요청한다.
- 두 요청이 거의 동시에 DB를 조회한다.
- 두 요청 모두 좌석이 AVAILABLE 이라고 판단한다.
- 두 요청 모두 좌석 선점 또는 예약 생성에 성공한다.

이 경우 한 좌석에 대해 두 예약이 동시에 성립할 수 있으며,  
이는 명백한 데이터 정합성 문제다.

#### 문제 유형
- Race Condition
- Lost Update 성격의 문제
- 최종적으로는 “한 좌석은 한 명만 선점 가능하다”는 비즈니스 규칙 위반

---

### 3.2 유저 잔액 차감

두 번째 핵심 동시성 이슈는 **유저 잔액 차감**이다.

예시 상황:

- 사용자 잔액이 10,000원이다.
- 같은 유저가 동시에 두 개의 결제 요청을 보낸다.
- 각 요청은 모두 현재 잔액이 10,000원이라고 읽는다.
- 각 요청이 각각 7,000원 결제가 가능하다고 판단한다.
- 결과적으로 잔액이 중복 차감되어 음수가 되거나 정합성이 깨질 수 있다.

#### 문제 유형
- Race Condition
- Lost Update
- 잔액 정합성 붕괴

---

## 4. 동시성 문제가 발생하는 이유

동시성 문제는 보통 다음 패턴에서 발생한다.

1. 데이터를 읽는다.
2. 현재 상태를 기준으로 비즈니스 판단을 한다.
3. 값을 수정한다.
4. 저장한다.

문제는 **1번과 3번 사이에 다른 요청이 끼어들 수 있다는 점**이다.

### 4.1 좌석 예약에서의 문제

좌석 예약은 일반적으로 아래 흐름을 가진다.

1. 좌석 조회
2. 좌석 상태 확인
3. 사용 가능하다고 판단
4. 좌석 상태를 HELD 또는 RESERVED로 변경
5. 예약 저장

두 트랜잭션이 동시에 같은 좌석을 조회하면,  
둘 다 사용 가능하다고 판단할 수 있다.

### 4.2 잔액 차감에서의 문제

잔액 차감도 동일하다.

1. 사용자 잔액 조회
2. 잔액이 충분한지 확인
3. 차감 수행
4. 저장

두 요청이 동시에 같은 잔액을 읽으면  
각 요청이 “차감 가능”이라고 오판할 수 있다.

---

## 5. 해결 후보 분석

---

## 5.1 좌석 선점 문제 해결 후보

### 후보 1. 애플리케이션 레벨 락

예:
- synchronized
- ReentrantLock
- 서버 메모리 기반 락

#### 장점
- 구현이 비교적 단순할 수 있다.

#### 단점
- 서버가 여러 대인 경우 락이 공유되지 않는다.
- 다중 인스턴스 환경에서 안전하지 않다.
- 분산 환경 대응이 어렵다.

#### 결론
본 프로젝트는 다중 인스턴스 환경도 고려해야 하므로 적합하지 않다.

---

### 후보 2. Optimistic Lock

버전 필드 등을 사용해 수정 시점에 충돌 여부를 감지하는 방식이다.

#### 장점
- DB 락을 오래 잡지 않아 성능상 유리하다.
- 충돌이 적으면 효율적이다.

#### 단점
- 같은 인기 좌석에 동시 요청이 몰리면 충돌이 빈번할 수 있다.
- 충돌 후 retry 처리 비용이 발생한다.
- “하나만 성공하면 되는 좌석 선점”에는 불필요한 재시도가 많아질 수 있다.

#### 결론
좌석처럼 충돌 가능성이 높은 자원에는 우선순위가 낮다.

---

### 후보 3. Pessimistic Lock

특정 좌석 row를 먼저 잠그고,  
다른 트랜잭션이 동시에 수정하지 못하도록 하는 방식이다.

예:
- `SELECT ... FOR UPDATE`
- JPA `PESSIMISTIC_WRITE`

#### 장점
- 같은 좌석에 대한 동시 접근을 순차적으로 처리할 수 있다.
- 한 요청이 처리되는 동안 다른 요청은 대기하게 되어 정합성을 지키기 쉽다.
- “동시에 두 명이 같은 좌석을 잡는 문제”를 가장 직접적으로 막을 수 있다.

#### 단점
- 락 경합이 많아질 수 있다.
- 트랜잭션이 길면 성능 저하 가능성이 있다.
- 여러 자원을 잘못된 순서로 잠그면 데드락 위험이 있다.

#### 결론
좌석 선점 문제에는 가장 적합한 후보이다.

---

## 5.2 유저 잔액 차감 문제 해결 후보

### 후보 1. Pessimistic Lock

사용자 잔액 row를 잠근 후 차감하는 방식이다.

#### 장점
- 정합성을 직관적으로 보장하기 쉽다.
- 동시에 한 사용자 잔액을 수정하는 요청을 순차 처리할 수 있다.

#### 단점
- 잔액 차감 요청이 많아질 경우 락 경합이 커질 수 있다.
- 사용자 관련 트랜잭션이 길어지면 병목이 생길 수 있다.

#### 결론
가능한 해결책이지만, 우선 후보는 아니다.

---

### 후보 2. Optimistic Lock

사용자 엔티티에 버전 필드를 두고,  
업데이트 시 읽은 시점과 저장 시점 사이의 변경 여부를 감지한다.

예:
- JPA `@Version`

#### 장점
- DB 락을 오래 잡지 않는다.
- 사용자별 자원이 분산되어 있어 충돌 범위가 비교적 작다.
- 일반적인 잔액 차감 로직에 잘 맞는다.

#### 단점
- 충돌 시 재시도 또는 실패 처리가 필요하다.
- 같은 사용자가 매우 짧은 시간에 다수 요청을 보내면 충돌이 자주 발생할 수 있다.

#### 결론
유저 잔액 차감 문제에는 가장 적합한 후보이다.

---

## 6. 최종 해결 방식 선정

### 6.1 좌석 선점: Pessimistic Lock 선택

좌석은 동일 자원에 경쟁이 집중될 가능성이 높고,  
결과적으로 **한 요청만 성공해야 하는 자원**이다.

따라서 좌석 선점에는 **Pessimistic Lock**을 적용한다.

#### 선정 이유
1. 인기 좌석에는 동시 접근이 많을 수 있다.
2. 현재 구현은 `SeatInventory`를 `scheduleId + seatNumber` 기준으로 조회하면서 `PESSIMISTIC_WRITE`를 적용하는 방향이 가장 자연스럽다.
3. 검증 순서와 예외 판단은 `ReservationFacade`가 담당하고, persistence adapter는 락 조회와 저장 연결에 집중하도록 분리한다.
2. 한 번의 경쟁에서 한 명만 성공해야 한다.
3. 충돌 후 재시도보다 선점 시점에 순차 처리하는 편이 명확하다.
4. 좌석 정합성 보장이 최우선이다.

---

### 6.2 유저 잔액 차감: Optimistic Lock 선택

유저 잔액은 좌석처럼 모든 요청이 하나의 자원에 몰리는 구조가 아니라,  
사용자별로 자원이 분산된다.

따라서 유저 잔액 차감에는 **Optimistic Lock**을 적용한다.

#### 선정 이유
1. 사용자별로 충돌 범위가 제한적이다.
2. 락 경합보다 버전 충돌 감지가 더 자연스럽다.
3. JPA의 `@Version`으로 구현하기 쉽다.
4. 비관적 락보다 성능상 부담이 적다.

---

## 7. 트랜잭션 관점의 고려사항

동시성 문제 해결에서 락만큼 중요한 것이 트랜잭션 경계다.

### 7.1 트랜잭션은 짧게 유지해야 한다

트랜잭션이 길어지면:
- 락 보유 시간이 길어진다.
- 다른 요청이 오래 대기한다.
- 데드락 가능성이 커진다.

따라서 좌석 선점과 결제 관련 트랜잭션은  
조회 → 검증 → 변경 → 저장 흐름을 최대한 짧게 유지해야 한다.

---

### 7.2 락 획득 순서는 일관되어야 한다

여러 자원을 동시에 잠그는 경우, 락 순서가 다르면 데드락이 발생할 수 있다.

예를 들어:
- 트랜잭션 A: 좌석 → 예약 순서
- 트랜잭션 B: 예약 → 좌석 순서

이런 식으로 순서가 섞이면 위험하다.

따라서 자원 잠금 순서를 일관되게 유지해야 한다.

## 8. STEP10 구현 계획

STEP10에서는 STEP09에서 정리한 해결 방안을 실제로 구현하고,  
통합 테스트를 통해 검증해야 한다.

### 8.1 좌석 선점 구현 계획
- 좌석 조회 repository에 비관적 락 적용
- 같은 좌석에 대해 동시에 여러 예약 요청이 들어왔을 때
    - 한 요청만 성공
    - 나머지는 실패하도록 구현
- 통합 테스트 작성
    - 동일 좌석에 대한 동시 요청 시나리오
    - 최종 성공 건수 및 좌석 상태 검증

### 8.2 유저 잔액 차감 구현 계획
- 사용자 엔티티에 `@Version` 적용
- 동시 결제 요청 시 버전 충돌 감지
- 잔액 음수 방지
- 통합 테스트 작성
    - 동일 유저에 대한 동시 결제 요청 시나리오
    - 최종 잔액 및 성공/실패 건수 검증

## 10. 결론

본 서비스에서 가장 중요한 동시성 문제는 다음 두 가지다.

1. 같은 좌석에 대한 중복 선점 문제
2. 같은 유저 잔액에 대한 중복 차감 문제

각 문제의 특성을 분석한 결과 다음과 같은 해결 방안을 선정했다.

- 좌석 선점: **Pessimistic Lock**
- 유저 잔액 차감: **Optimistic Lock**

이후 STEP10에서는 위 설계를 실제 코드로 구현하고,  
통합 테스트를 통해 해결 효과를 검증한다.
