# 콘서트 예약 서비스 트랜잭션 시퀀스

## 1. 문서 목적

이 문서는 주요 유스케이스의 처리 순서, 트랜잭션 경계, 재검증 지점을 정리한다.

기준 원칙은 아래와 같다.

- 정합성 판정은 트랜잭션 안에서 수행한다.
- 스케줄러는 정리 역할만 수행한다.
- 좌석 선점은 조건부 업데이트를 우선 사용한다.
- 잔액 차감은 낙관적 락을 기본으로 사용한다.

## 2. 유저 대기열 토큰 발급

### 2.1 처리 목적

- 콘서트별 대기열에 진입시키고 토큰을 발급한다.

### 2.2 시퀀스

1. 사용자 존재 여부를 확인한다.
2. 콘서트 존재 여부를 확인한다.
3. 해당 콘서트의 다음 대기 순번을 계산한다.
4. `QueueToken(WAITING)`을 생성한다.
5. 토큰 문자열과 대기번호를 반환한다.

### 2.3 트랜잭션 포인트

- 토큰 발급은 단일 트랜잭션으로 처리한다.
- 순번 계산은 DB 정렬 기준 또는 별도 시퀀스를 이용해 일관되게 관리한다.

## 3. 대기열 승격 보정

### 3.1 처리 목적

- 콘서트별 `ACTIVE` 슬롯을 설정값 이내로 유지하면서 `WAITING` 토큰을 순서대로 승격한다.

### 3.2 승격 정책

1. 콘서트별 `ACTIVE` 슬롯 최대 수를 설정값으로 관리한다.
2. 현재 `ACTIVE` 상태 토큰 수를 확인한다.
3. 현재 `ACTIVE` 수가 최대 수보다 작으면 승격 여유 슬롯 수를 계산한다.
4. 가장 작은 `queuePosition` 순서의 `WAITING` 토큰을 승격 후보로 조회한다.
5. 후보를 `ACTIVE`로 변경하고 `activatedAt`을 기록한다.
6. 필요 수만큼 반복하되, 매 변경 시점에 슬롯 수를 다시 검증한다.

### 3.3 슬롯이 비는 조건

- 결제 성공으로 토큰이 `USED`가 되는 경우
- 토큰 유효시간이 지나 `EXPIRED`가 되는 경우
- 운영 정책에 따라 `ACTIVE` 상태를 강제 종료하는 경우

### 3.4 승격 수행 시점

- 대기번호 조회 API 호출 시
- 예약 또는 결제 API의 토큰 검증 직전 보정 로직에서
- 별도 스케줄러 또는 배치 작업에서

### 3.5 트랜잭션 포인트

- 승격은 단일 트랜잭션으로 처리한다.
- 조회 기반 보정이라도 최종 `ACTIVE` 전환은 트랜잭션 안에서 수행한다.
- 동시 승격 시도를 고려해 같은 콘서트 기준으로 슬롯 수를 다시 확인해야 한다.

## 4. 대기번호 조회

### 4.1 처리 목적

- 사용자의 현재 콘서트별 대기 상태와 순번을 조회한다.

### 4.2 시퀀스

1. 토큰 또는 유저 기준으로 대기열 데이터를 조회한다.
2. 현재 상태가 `WAITING`, `ACTIVE`, `USED`, `EXPIRED` 중 무엇인지 확인한다.
3. 응답을 반환한다.

### 4.3 트랜잭션 포인트

- 읽기 전용 트랜잭션으로 충분하다.

## 5. 예약 가능 날짜 조회

### 5.1 처리 목적

- 콘서트별 예약 가능한 날짜 목록을 제공한다.

### 5.2 시퀀스

1. 콘서트의 회차 목록을 조회한다.
2. 날짜 목록을 응답으로 반환한다.

### 5.3 트랜잭션 포인트

- 읽기 전용 트랜잭션으로 처리한다.

## 6. 예약 가능 좌석 조회

### 6.1 처리 목적

- 특정 회차의 현재 예약 가능한 좌석 목록을 제공한다.

### 6.2 시퀀스

1. 회차 존재 여부를 확인한다.
2. `SeatInventory`를 조회한다.
3. `AVAILABLE` 상태 좌석을 포함한다.
4. `HELD` 상태라도 만료된 좌석은 예약 가능으로 간주할 수 있도록 조회 조건에 반영한다.
5. 결과를 응답으로 반환한다.

### 6.3 트랜잭션 포인트

- 조회 API는 읽기 전용 트랜잭션으로 처리한다.
- 다만 응답은 참고용이며, 실제 선점 가능 여부는 예약 트랜잭션 안에서 다시 판단한다.

## 7. 좌석 예약 요청

### 7.1 처리 목적

- 사용자가 좌석을 약 5분 동안 임시 배정받는다.

### 7.2 시퀀스

1. 요청 토큰을 조회한다.
2. 필요 시 해당 콘서트에 대한 승격 보정 로직을 수행한다.
3. 토큰이 해당 콘서트의 `ACTIVE` 상태인지 확인한다.
4. 사용자가 이미 활성 임시 배정을 가지고 있는지 확인한다.
5. 대상 회차와 좌석 번호 유효성을 확인한다.
6. 현재 시각과 만료 시각을 계산한다.
7. `SeatInventory`에 조건부 업데이트를 수행한다.
8. 업데이트 결과가 1건이면 선점 성공으로 본다.
9. `Reservation(TEMPORARY)`를 생성한다.
10. 예약 정보와 만료 시각을 반환한다.

### 7.3 실패 조건

- 토큰이 없거나 `ACTIVE`가 아니다.
- 이미 다른 임시 배정을 보유 중이다.
- 좌석이 이미 확정되었거나 유효한 홀드 상태다.

### 7.4 트랜잭션 포인트

- 1개 트랜잭션으로 처리한다.
- 핵심은 `SeatInventory` 조건부 업데이트와 `Reservation` 생성이 같은 트랜잭션에 있어야 한다는 점이다.

## 8. 잔액 충전

### 8.1 처리 목적

- 사용자의 잔액을 증가시킨다.

### 8.2 시퀀스

1. 사용자 잔액 엔티티를 조회한다.
2. 충전 금액 유효성을 검증한다.
3. 잔액을 증가시킨다.
4. `BalanceTransaction(CHARGE)`를 생성한다.
5. 결과 잔액을 반환한다.

### 8.3 트랜잭션 포인트

- 1개 트랜잭션으로 처리한다.

## 9. 잔액 조회

### 9.1 처리 목적

- 사용자의 현재 잔액을 조회한다.

### 9.2 시퀀스

1. `UserBalance`를 조회한다.
2. 현재 잔액을 반환한다.

### 9.3 트랜잭션 포인트

- 읽기 전용 트랜잭션으로 처리한다.

## 10. 결제 요청

### 10.1 처리 목적

- 임시 배정된 좌석을 최종 확정한다.

### 10.2 시퀀스

1. 요청 토큰을 조회한다.
2. 필요 시 해당 콘서트에 대한 승격 보정 로직을 수행한다.
3. 토큰이 해당 콘서트의 `ACTIVE` 상태인지 확인한다.
4. 예약 정보를 조회한다.
5. 예약이 본인 소유인지 확인한다.
6. 예약 상태가 `TEMPORARY`인지 확인한다.
7. 예약 만료 시각이 현재 시각 이후인지 확인한다.
8. 좌석 정보를 조회한다.
9. 좌석이 `HELD` 상태이며 본인에게 배정되어 있는지 확인한다.
10. 좌석 홀드 만료 시각이 현재 시각 이후인지 확인한다.
11. `UserBalance`를 조회한다.
12. 잔액이 좌석 가격 이상인지 확인한다.
13. 잔액을 차감한다.
14. `Payment(SUCCESS)`를 생성한다.
15. `BalanceTransaction(USE)`를 생성한다.
16. `SeatInventory`를 `RESERVED`로 변경한다.
17. `Reservation`을 `CONFIRMED`로 변경한다.
18. `QueueToken`을 `USED` 또는 `EXPIRED`로 변경한다.
19. 응답을 반환한다.

### 10.3 실패 조건

- 토큰이 유효하지 않다.
- 예약이 본인 소유가 아니다.
- 예약 또는 좌석 홀드가 이미 만료되었다.
- 잔액이 부족하다.
- 낙관적 락 충돌이 발생했다.

### 10.4 트랜잭션 포인트

- 1개 트랜잭션으로 처리한다.
- 아래 변경은 모두 원자적으로 성공 또는 실패해야 한다.
- 잔액 차감
- 결제 생성
- 사용 이력 생성
- 좌석 확정
- 예약 확정
- 토큰 종료

## 11. 만료 스케줄러

### 11.1 처리 목적

- 만료된 임시 배정과 예약 상태를 정리한다.

### 11.2 시퀀스

1. 현재 시각 기준 만료된 `SeatInventory(HELD)`를 조회 또는 일괄 갱신한다.
2. 해당 좌석을 `AVAILABLE`로 되돌린다.
3. 현재 시각 기준 만료된 `Reservation(TEMPORARY)`를 `EXPIRED`로 변경한다.
4. 필요 시 만료 토큰을 정리한다.

### 11.3 트랜잭션 포인트

- 스케줄러는 배치 단위 트랜잭션으로 실행할 수 있다.
- 스케줄러가 늦더라도 요청 시점 재검증이 최종 판정 역할을 한다.

## 12. 시퀀스 다이어그램 초안

### 12.1 좌석 예약

```text
Client
  -> Reservation API
  -> QueueToken 조회
  -> 필요 시 승격 보정
  -> ACTIVE 검증
  -> 사용자 활성 임시 배정 존재 여부 확인
  -> SeatInventory 조건부 업데이트
  -> Reservation 생성
  -> 응답
```

### 12.2 결제

```text
Client
  -> Payment API
  -> QueueToken 조회
  -> 필요 시 승격 보정
  -> ACTIVE 검증
  -> Reservation 조회 및 만료 검증
  -> SeatInventory 조회 및 홀드 검증
  -> UserBalance 조회
  -> 잔액 차감
  -> Payment 생성
  -> BalanceTransaction 생성
  -> SeatInventory RESERVED 변경
  -> Reservation CONFIRMED 변경
  -> QueueToken USED 변경
  -> 응답
```
