# STEP10 - Finalize
## 동시성 제어 구현 및 통합 테스트 검증 계획

---

## 1. 문서 목적

이 문서는 STEP09에서 정리한 동시성 문제 해결 방안을 실제 애플리케이션에 구현하고,  
통합 테스트를 통해 정합성이 유지되는지 검증하기 위한 계획과 기준을 정리한 문서이다.

STEP10의 핵심 목표는 다음과 같다.

- STEP09에서 선정한 동시성 해결 방안을 실제 코드로 구현
- 동시성 문제가 드러나는 테스트 시나리오 작성
- 해결 전/후의 차이를 통합 테스트로 검증
- 최종적으로 애플리케이션의 운영 안정성을 높이는 방향으로 마무리

---

## 2. STEP09 요약

STEP09 분석 결과, 콘서트 예약 서비스에서 가장 중요한 동시성 문제는 다음 두 가지로 정리되었다.

### 2.1 좌석 선점
- 문제: 같은 좌석에 대한 중복 예약 시도
- 해결 방식: **Pessimistic Lock**

### 2.2 유저 잔액 차감
- 문제: 동일 유저 잔액에 대한 중복 차감
- 해결 방식: **Optimistic Lock**

이 STEP10 문서는 위 설계를 코드와 테스트로 검증하는 데 초점을 둔다.

---

## 3. 구현 목표

### 3.1 좌석 선점 구현 목표
같은 회차의 같은 좌석에 대해 동시에 여러 예약 요청이 들어와도  
최종적으로 오직 한 요청만 성공해야 한다.

즉:
- 하나의 좌석은 동시에 한 명만 임시 점유 또는 확정 가능해야 한다.
- 나머지 요청은 실패해야 한다.

---

### 3.2 유저 잔액 차감 구현 목표
같은 유저에 대해 동시에 여러 결제 요청이 들어와도  
잔액은 음수가 되지 않아야 하며, 성공 가능한 요청만 처리되어야 한다.

즉:
- 읽은 잔액 기준으로 중복 차감이 발생하면 안 된다.
- 버전 충돌 또는 잔액 부족 처리를 통해 정합성이 유지되어야 한다.

---

## 4. 구현 대상

### 4.1 좌석 선점 구현 대상

- 좌석 상태 변경 로직

### 4.2 유저 잔액 차감 구현 대상

- 잔액 차감 로직

## 5. 좌석 선점 구현 계획

## 5.1 핵심 아이디어
좌석 row에 대해 비관적 락을 걸어,  
동시에 같은 좌석을 선점하려는 요청이 순차적으로 처리되도록 한다.

예시 방향:
- `SELECT ... FOR UPDATE`
- 또는 JPA `PESSIMISTIC_WRITE`

---

## 5.2 구현 포인트

### 조회
- `scheduleId + seatNumber` 기준으로 좌석 조회
- 조회 시 락 획득
- 현재 구현 기준으로는 `SeatInventoryJpaRepository`에서 `PESSIMISTIC_WRITE` 조회 메서드를 사용한다.

### 검증
- 좌석이 존재하는지 확인
- 상태가 AVAILABLE인지 확인
- 이미 RESERVED인지 확인
- HELD 상태라면 만료 여부 확인

### 변경
- 좌석 상태를 HELD 또는 RESERVED로 변경
- 예약 엔티티 저장
- 검증 순서와 저장 순서의 orchestration은 `ReservationFacade`가 담당한다.

### 주의점
- 트랜잭션은 최대한 짧게 유지
- 락 획득 후 불필요한 외부 작업 금지
- 예외 발생 시 rollback 보장

---

## 5.3 기대 결과

동일 좌석에 대해 동시에 여러 요청이 들어와도:
- 한 요청만 성공
- 나머지는 실패

최종 상태:
- 좌석은 한 번만 점유됨
- 예약은 한 건만 성공적으로 생성됨

---

## 6. 유저 잔액 차감 구현 계획

## 6.1 핵심 아이디어
사용자 엔티티에 버전 필드를 두고,  
동시에 잔액 차감이 일어날 경우 버전 충돌로 감지한다.

예시 방향:
- JPA `@Version`

---

## 6.2 구현 포인트

### 조회
- `userId` 기준 사용자 조회

### 검증
- 사용자가 존재하는지 확인
- 현재 잔액이 결제 금액 이상인지 확인

### 변경
- 잔액 차감
- 결제 엔티티 저장

### 충돌 처리
- 동시에 다른 트랜잭션이 먼저 업데이트했다면 버전 충돌 발생
- 충돌 시:
    - 실패 처리
    - 또는 제한적 재시도

---

## 6.3 기대 결과

같은 사용자에 대해 동시에 여러 결제 요청이 들어와도:
- 실제 잔액 범위 안에서만 성공
- 음수 잔액 방지
- 중복 차감 방지

## 7. 통합 테스트 전략

STEP10의 핵심은 “동시성 문제를 드러낼 수 있는 통합 테스트”를 작성하는 것이다.

---

## 7.1 좌석 선점 통합 테스트

### 테스트 목표
동시에 같은 좌석을 예약 시도했을 때,  
단 한 요청만 성공하는지 검증한다.

### 테스트 시나리오
1. 동일 회차, 동일 좌석 준비
2. 여러 스레드가 동시에 예약 요청
3. 모든 요청 종료 후 결과 확인

### 검증 포인트
- 성공 건수는 1건이어야 함
- 실패 건수는 N-1건이어야 함
- 좌석 상태는 최종적으로 HELD 또는 RESERVED 1건만 반영
- 예약 데이터도 1건만 생성되어야 함

---

## 7.2 유저 잔액 차감 통합 테스트

### 테스트 목표
동시에 여러 결제 요청이 들어왔을 때,  
잔액 정합성이 깨지지 않는지 검증한다.

### 테스트 시나리오
1. 사용자 잔액 준비
2. 여러 스레드가 동시에 결제 요청
3. 모든 요청 종료 후 결과 확인

### 검증 포인트
- 잔액은 음수가 되지 않아야 함
- 총 차감 금액이 원래 잔액을 초과하지 않아야 함
- 성공 가능한 요청 수만 성공해야 함
- 버전 충돌 또는 잔액 부족 예외가 의도대로 발생해야 함

## 8. 테스트 환경 전략

통합 테스트는 가능한 한 독립적으로 수행되어야 한다.

### 목표
- 테스트 실행 전 외부 DB 준비에 의존하지 않기
- 반복 실행 시 같은 결과 보장
- 테스트 환경 자체가 정합성을 해치지 않도록 구성

### 방향
- Testcontainers 또는 독립적인 테스트 DB 환경 활용
- 테스트 시작 시 데이터 초기화
- 테스트 간 상태 오염 방지
