# Booking Concert

JPA 기반 콘서트 예약 서비스 프로젝트다. 핵심 목표는 콘서트별 대기열, 좌석 임시 배정, 결제, 예약 만료 처리, 동시성 제어를 일관된 구조로 설계하고 구현하는 것이다.

## 1. 프로젝트 목표

- 콘서트별 대기열을 통해 예약 가능 사용자를 제어한다.
- `SeatInventory` 중심으로 현재 좌석 상태를 단일 기준으로 관리한다.
- 결제 전 약 5분 동안 좌석을 임시 배정하고, 만료 시 자동 해제한다.
- 다중 인스턴스 환경에서도 좌석 중복 배정과 잔액 중복 차감을 방지한다.
- 테스트 가능한 구조를 유지하고 핵심 비즈니스 로직을 외부 기술로부터 분리한다.

## 2. 아키텍처 선택

이 프로젝트는 도메인 중심의 가벼운 클린 아키텍처를 따른다.

계층 구조:

- `presentation`
- `application`
- `domain`
- `infrastructure`

선택 근거:

- 예약, 결제, 대기열, 만료 처리 같은 핵심 비즈니스 규칙을 프레임워크 코드와 분리하기 쉽다.
- 의존성이 단방향으로 흐르도록 설계할 수 있다.
- 테스트에서 외부 저장소나 스케줄러를 Mock 또는 Stub으로 대체하기 쉽다.
- 동시성 제어, 트랜잭션 경계, 예외 처리 정책을 application 계층 중심으로 일관되게 유지할 수 있다.

## 3. 계층별 책임

### 3.1 presentation

- HTTP 요청과 응답 처리
- 요청 DTO 검증
- 인증 또는 토큰 헤더 해석
- 공통 예외를 HTTP 응답으로 변환

주의점:

- 비즈니스 판단을 두지 않는다.

### 3.2 application

- 유스케이스 실행
- 트랜잭션 경계 관리
- 도메인 서비스 조합
- 외부 포트 호출 조정
- 예외 전환과 이벤트 발행

주의점:

- 화면, DB, 스케줄러 기술 세부사항에 직접 의존하지 않는다.

### 3.3 domain

- 엔티티, 값 객체, 상태 enum
- 도메인 규칙
- 좌석 선점 가능 조건, 결제 가능 조건, 토큰 사용 가능 조건 같은 핵심 판단

주의점:

- Spring, JPA, HTTP 같은 외부 기술 의존을 두지 않는다.

### 3.4 infrastructure

- JPA 엔티티 및 리포지토리 구현
- 조건부 업데이트 쿼리
- 스케줄러 구현
- 로깅, 이벤트 발행, 외부 시스템 연동

## 4. 의존성 원칙

- 의존성은 `presentation -> application -> domain` 방향으로만 흐른다.
- `infrastructure`는 `application`과 `domain`에서 정의한 포트 또는 인터페이스를 구현한다.
- 의존성 주입은 생성자 기반 DI를 기본으로 한다.
- 테스트에서는 application 서비스에 Mock 또는 Stub 구현체를 주입해 단위 테스트를 수행할 수 있도록 설계한다.

## 5. 핵심 설계 방향

### 5.1 좌석 상태 관리

- `SeatInventory`를 현재 좌석 상태의 단일 기준으로 사용한다.
- 좌석 선점은 조건부 업데이트를 우선 적용한다.
- 좌석 조회 결과는 참고용이며, 실제 예약 성공 여부는 트랜잭션 안에서 재검증한다.

### 5.2 대기열

- 대기열은 콘서트별로 분리한다.
- 대기열 토큰은 좌석 예약과 결제 시에만 사용한다.
- 결제 완료 후 토큰은 `USED` 또는 `EXPIRED`로 종료한다.

### 5.3 잔액 차감

- 잔액 차감은 `@Version` 기반 낙관적 락을 기본안으로 사용한다.
- 충돌 발생 시 재시도 또는 비즈니스 실패 응답 전략을 선택할 수 있다.

### 5.4 만료 처리

- 만료 처리는 스케줄러와 요청 시점 재검증을 병행한다.
- 스케줄러는 정리 역할만 수행한다.
- 실제 정합성 판정은 예약 및 결제 트랜잭션 안에서 수행한다.

### 5.5 무결성 검증

- DB 외래키 제약은 두지 않는다.
- 무결성 검증 책임은 애플리케이션 서비스와 도메인 규칙에서 수행한다.
- JPA 엔티티는 연관관계를 최소화하고 FK ID 중심으로 설계한다.

## 6. 트랜잭션 및 보상 처리 전략

- 예약 요청은 좌석 조건부 업데이트와 예약 이력 생성을 하나의 트랜잭션으로 묶는다.
- 결제 요청은 토큰 검증, 예약 상태 검증, 좌석 상태 검증, 잔액 차감, 결제 생성, 좌석 확정, 예약 확정, 토큰 종료를 하나의 트랜잭션으로 묶는다.
- 실패 시 부분 성공을 허용하지 않고 전체 롤백을 기본 전략으로 한다.
- 비동기 후처리가 필요한 경우에는 트랜잭션 커밋 후 이벤트를 발행한다.

보상 처리 기본안:

- 동기 트랜잭션 내부 작업은 롤백으로 일관성 유지
- 비동기 후처리 실패는 재시도 가능한 이벤트 소비 구조로 분리

## 7. 동시성 전략

- 좌석 선점: 조건부 업데이트 기반
- 잔액 차감: 낙관적 락 기반
- 만료 판정: 요청 시점 재검증
- 스케줄러: 정리용 배치 작업

주요 위험 구간:

- 같은 좌석 동시 예약
- 한 사용자 다중 임시 배정
- 잔액 동시 차감
- 만료 직전 결제
- 스케줄러와 사용자 요청 충돌

## 8. 예외 처리 전략

의미 있는 커스텀 예외를 사용하고 presentation 계층에서 일관된 응답으로 변환한다.

예시:

- `QueueTokenNotActiveException`
- `SeatAlreadyHeldException`
- `SeatAlreadyReservedException`
- `ReservationExpiredException`
- `InsufficientBalanceException`
- `OptimisticLockConflictException`

원칙:

- 도메인 규칙 위반은 명확한 비즈니스 예외로 표현한다.
- 인프라 예외는 application 계층에서 의미 있는 예외로 전환한다.
- 공통 예외 핸들러에서 에러 코드와 메시지를 표준화한다.

## 9. 로깅 전략

- 요청 진입과 종료에 대한 기본 API 로그
- 좌석 선점 성공 또는 실패 로그
- 결제 성공 또는 실패 로그
- 낙관적 락 충돌 로그
- 만료 스케줄러 실행 결과 로그
- 이벤트 발행 및 소비 실패 로그

원칙:

- 사용자 식별자, 콘서트 ID, 회차 ID, 좌석 번호, 예약 ID, 결제 ID를 구조적으로 기록한다.
- 민감 정보는 로그에 남기지 않는다.
- 정상 흐름은 `INFO`, 충돌과 재시도는 `WARN`, 시스템 실패는 `ERROR`로 구분한다.

## 10. 이벤트 기반 확장 포인트

현재 핵심 정합성은 동기 트랜잭션으로 처리한다. 다만 아래 지점은 이벤트 기반 또는 비동기 처리로 확장할 수 있다.

- 결제 완료 후 알림 발송
- 예약 만료 후 알림 발송
- 대기열 활성 전환 후 알림 발송
- 결제 집계 또는 통계 적재
- 감사 로그 적재

권장 원칙:

- 좌석 확정, 잔액 차감 같은 핵심 상태 변경은 동기 트랜잭션
- 알림, 통계, 후처리 적재는 비동기 이벤트

## 11. 테스트 전략 요약

- domain 규칙은 순수 단위 테스트로 검증한다.
- application 서비스는 Mock 또는 Stub 기반 테스트로 검증한다.
- 동시성 제어는 통합 테스트 또는 멀티스레드 테스트로 검증한다.
- 조건부 업데이트, 낙관적 락, 만료 재검증 시나리오를 우선 테스트한다.
